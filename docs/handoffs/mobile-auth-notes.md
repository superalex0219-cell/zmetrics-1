## Пункт 1 — JWT issuer validation

### Что изменилось в бэкенде
`jwt.decode()` теперь проверяет поле `iss` (issuer) в токене. Принимается только токен, выпущенный конкретным realm'ом:
```
iss = http://<KEYCLOAK_HOST>/realms/zmetrics
```

### Что значит для Flutter-приложения

**Конфигурация Keycloak во Flutter** должна совпадать с `KEYCLOAK_URL` + `KEYCLOAK_REALM` из `infra/.env`.

```dart
// Пример: keycloak_service.dart
final keycloak = KeycloakService(
  serverUrl: 'http://10.0.2.2:8080',  // эмулятор — 10.0.2.2, не localhost
  realm: 'zmetrics',
  clientId: 'zmetrics-mobile',
);
```

**Новые коды ошибок от бэкенда:**

| Ситуация | HTTP | Тело |
|----------|------|------|
| Токен от другого realm | 401 | `{"detail": "Invalid token: …"}` |
| Токен истёк | 401 | `{"detail": "Token has expired"}` |
| Нет заголовка Authorization | 401 | `{"detail": "Not authenticated"}` |

**Рекомендуемая обработка:**
```dart
if (response.statusCode == 401) {
  await keycloak.refreshToken();  // попробовать обновить токен
  // если refresh тоже 401 → logout + экран логина
}
```

### Ничего не меняется
Структура токена, endpoint'ы, форматы ответов — всё прежнее.

## Пункт 2 — Повторное назначение роли (re-grant fix)

### Что было сломано
Если администратор отзывал доступ пользователя к карьеру, а потом снова выдавал — Postgres падал с ошибкой уникальности. Бэкенд возвращал 500.

### Что изменилось в бэкенде
Ограничение уникальности на таблице `quarry_user_access` сделано частичным:
```sql
UNIQUE (user_id, quarry_id) WHERE revoked_at IS NULL
```
Старые отозванные строки остаются в истории, новая активная строка создаётся без конфликта.

### Что значит для Flutter-приложения

**Сценарий "пользователя кикнули и вернули":**

1. Пользователь не видит карьер → получил `revoked_at` от админа  
2. Пользователь снова видит карьер → админ выдал доступ заново  
3. Пользователю **не нужен logout/login** — достаточно обновить список карьеров

```dart
// Pull-to-refresh на экране списка карьеров должен обращаться к API:
// GET /api/v1/quarries
// Бэкенд вернёт актуальный список согласно текущим правам в БД
```

**Важно:** роли хранятся в БД, не в JWT-токене. JWT содержит только `sub` (идентификатор пользователя). Это значит:
- Смена роли вступает в силу при следующем API-запросе, без перевыпуска токена
- Кешировать список карьеров можно, но TTL кэша держи небольшим (30–60 сек) чтобы изменения доступа отражались быстро

## Пункт 3 — Миграции и seed ролей

### Что изменилось в бэкенде
Созданы две Alembic-миграции:
- `0001` — полная схема БД (все таблицы, типы, индексы)
- `0002` — seed стандартных ролей: `user/1`, `surveyor/2`, `blaster/3`, `admin/4`

Без `0002` таблица `role` пуста → все `require_quarry_role`-проверки возвращают 403 даже при корректном токене. Теперь схема и данные применяются автоматически при поднятии стека.

### Что значит для Flutter-приложения

**Роли — это уровни доступа per-quarry.** Один пользователь может быть `surveyor` на карьере А и `user` на карьере Б. В JWT никакого поля `role` нет — роль бэкенд читает из БД при каждом запросе.

| Роль | Уровень | Что может на этом карьере |
|------|---------|--------------------------|
| `user` | 1 | Читать отчёты, просматривать рекомендации |
| `surveyor` | 2 | Загружать фото, запускать анализ |
| `blaster` | 3 | Создавать паспорта БВР, создавать участки, комментировать |
| `admin` | 4 | Всё выше + выдавать доступ, одобрять паспорта |

**Для UX:** если бэкенд вернул 403 — пользователю не хватает роли на данном карьере. Показывай сообщение "Недостаточно прав", а не "Ошибка сети".

```dart
if (response.statusCode == 403) {
  showSnackbar('Нет доступа к этому разделу');
  // НЕ logout — токен живой, просто нет прав
}
```

### Ничего не меняется в API
Endpoint'ы те же. Роль — это только серверная проверка, клиенту передавать её не нужно.

## Пункт 4 — Тесты auth-слоя

### Что изменилось в бэкенде
Написано 10 автотестов (`tests/test_auth.py`). Покрывают: протухший токен, невалидную подпись, авто-провизионирование, деактивированного пользователя, отсутствие `sub`, и все четыре ветки `require_quarry_role` (нет доступа / отозван / низкая роль / достаточная роль). **41/41 тестов зелёные.**

### Что значит для Flutter-приложения

| Поведение | Гарантировано тестом |

**Для Flutter-разработчика:** эти сценарии не надо угадывать — они теперь задокументированы кодом. При сомнениях смотри `backend/tests/test_auth.py`.

## Пункт 5 — Создание карьера требует ADMIN

### Что изменилось в бэкенде
`POST /api/v1/quarries` теперь требует роли `admin` хотя бы на одном из существующих карьеров. Раньше любой аутентифицированный пользователь мог создать карьер.

### Что значит для Flutter-приложения

Кнопку "Создать карьер" показывай **только** если пользователь является admin хотя бы на одном карьере. Признак — в ответе `GET /api/v1/quarries` есть хотя бы один элемент (значит у пользователя есть доступ). Точнее можно будет определить через будущий endpoint `GET /users/me/roles`, но пока:

```dart
// Простая эвристика: если quarries непуст → пользователь что-то видит → скорее всего admin
// Но кнопку лучше показывать всегда, а 403 обрабатывать gracefully:
if (response.statusCode == 403) {
  showSnackbar('Только администратор может создавать карьеры');
}
```

**Новое поведение при вызове `POST /quarries` без admin-роли:**
```
HTTP 403
{"detail": "Admin access required"}
```

## Пункт 6 — Worker автоматически создаёт Report и Recommendation

### Что изменилось в бэкенде
Раньше после завершения `AnalysisJob` в воркере создавался только `AnalysisResult`. `Report` и `Recommendation` создавались только через `POST /admin/dev-seed`. Теперь воркер создаёт их автоматически.

Цепочка после успешного пайплайна:
```
AnalysisJob (completed)
  └─ AnalysisResult          ← создаётся в MockGranulometryStep
       └─ Report              ← НОВОЕ: создаётся в pipeline.py
            └─ Recommendation ← НОВОЕ: всегда status=requires_human_review
```

**Безопасность:** Recommendation создаётся с `status = "requires_human_review"` и без `parameter_suggestions`. Автоматически применить параметры БВР невозможно — требуется явное действие пользователя.

### Что значит для Flutter-приложения

**Полный happy path теперь работает:**

1. Surveyor загружает фото → `POST /capture-sessions/{id}/artifacts`
2. Surveyor запускает анализ → `POST /capture-sessions/{id}/jobs`
3. Воркер обрабатывает → ~2-3 сек для mock pipeline
4. Отчёт доступен автоматически → `GET /quarries/{id}/reports`

**Polling для получения результата:**
```dart
// Опрашивай статус job каждые 2 сек, пока не completed/failed
final job = await api.getJob(sessionId, jobId);
if (job.status == 'completed') {
  // Report уже создан — можно открывать список отчётов карьера
  await loadReports(quarryId);
}
```

**Важно для UX:** report появляется не сразу при `job.status == 'completed'` — он создаётся в той же транзакции, но если между commit в воркере и GET /reports пройдёт меньше ~100ms, данные могут ещё не реплицироваться на read-реплику (если она есть). На текущем стенде всё в одном Postgres — задержки нет.

**Заголовок отчёта** содержит `"⚠ Mock pipeline"` — это нормально, отображай его как есть.

## Пункт 7 — Выгрузка отчёта (`GET /reports/{id}/export`)

### Что добавлено в бэкенде
Новый endpoint: `GET /api/v1/reports/{report_id}/export`  
Требует роль **BLASTER+**. Возвращает скачиваемый JSON-файл со всеми данными отчёта.

> PDF-генерация — M2+. Сейчас JSON-export — это полноценный пакет данных, пригодный для создания PDF на клиенте или просмотра в любом инструменте.

Структура ответа:
```json
{
  "export_format": "json_placeholder",
  "note": "⚠ Mock pipeline — results are synthetic. PDF export available in M2.",
  "report": { "id": "...", "title": "...", "created_at": "..." },
  "analysis_result": {
    "p10_mm": 120.5, "p50_mm": 345.2, "p80_mm": 580.8,
    "confidence_score": 0.72,
    "size_distribution": [...]
  },
  "recommendations": [{ "id": "...", "status": "requires_human_review", ... }]
}
```

Заголовок ответа: `Content-Disposition: attachment; filename="report_<id>_<date>.json"`

### Что значит для Flutter-приложения

```dart
// Скачать отчёт
final response = await dio.get(
  '/api/v1/reports/$reportId/export',
  options: Options(responseType: ResponseType.bytes),
);
// response.data — байты JSON файла
// response.headers['content-disposition'] — имя файла

// Сохранить на устройство (например через path_provider + file_picker)
final dir = await getExternalStorageDirectory();
final file = File('${dir!.path}/report_$reportId.json');
await file.writeAsBytes(response.data);
```

**403 если нет роли BLASTER:** пользователь с ролью `user` не может скачать отчёт — покажи кнопку экспорта только для blaster/admin.

## Пункт 8 — Управление пользователями (PATCH + DELETE /admin/users/{id})

### Что добавлено в бэкенде

| Endpoint | Роль | Действие |
|----------|------|----------|
| `PATCH /api/v1/admin/users/{id}` | Admin+ (любой карьер) | Изменить `full_name` и/или `is_active` |
| `DELETE /api/v1/admin/users/{id}` | Admin+ (любой карьер) | Деактивировать аккаунт (`is_active = false`) |

`DELETE` не удаляет запись из БД — ставит `is_active = false`. Деактивированный пользователь получает 403 при следующем запросе (обрабатывается в `get_current_user`).

Нельзя деактивировать себя — вернёт 400.

Оба действия пишут запись в `AuditLog`.

### Что значит для Flutter-приложения

**Экран управления пользователями (только для admin):**

```dart
// Редактировать имя
await api.patch('/admin/users/$userId', {'full_name': 'Новое Имя'});

// Деактивировать пользователя
await api.delete('/admin/users/$userId');
// После этого пользователь получит 403 при следующем запросе
// и будет переброшен на экран "аккаунт деактивирован"
```

**Важно для обработки ошибок на клиенте:**

```dart
// При любом API-запросе кроме логина:
if (response.statusCode == 403 && 
    response.data['detail'] == 'Account is inactive') {
  // Разлогинить и показать экран "аккаунт заблокирован"
  await keycloak.logout();
  navigateTo('/account-disabled');
}
```

**Когда `is_active = false` вступает в силу:** немедленно, при следующем API-запросе. Текущая JWT-сессия не инвалидируется — это Keycloak-side операция (вне скоупа M1).

## Пункт 9 — `GET /api/v1/me/access` — роли пользователя по карьерам

### Зачем
Раньше мобильное приложение определяло права из глобальных realm-ролей Keycloak (`realm_access.roles` в JWT). Но роли в системе — **per-quarry**: один пользователь может быть `blaster` на карьере А и `user` на карьере Б. Realm-роли — грубый признак, не дающий точного ответа на вопрос «могу ли я нажать кнопку X для карьера Y?».

### Новый endpoint

```
GET /api/v1/me/access
Authorization: Bearer <token>
```

Ответ:
```json
[
  {
    "quarry_id": "3fa85f64-...",
    "quarry_name": "Карьер Гранитный",
    "role_name": "blaster",
    "role_level": 3
  },
  {
    "quarry_id": "7cb12a11-...",
    "quarry_name": "Карьер Северный",
    "role_name": "user",
    "role_level": 1
  }
]
```

Возвращает только карьеры с **активным** (не отозванным) доступом. Пустой массив = нет доступа ни к одному карьеру.

### Как использовать во Flutter

**Вызывай один раз при старте сессии, кэшируй локально:**

```dart
// При логине:
final myAccess = await api.getMyAccess(); 
// Сохрани в провайдер/bloc

// Проверка прав перед показом кнопки:
bool canExport(String quarryId) {
  final entry = myAccess.firstWhereOrNull((a) => a.quarryId == quarryId);
  return (entry?.roleLevel ?? 0) >= 3; // blaster+
}

bool canCreatePassport(String quarryId) {
  final entry = myAccess.firstWhereOrNull((a) => a.quarryId == quarryId);
  return (entry?.roleLevel ?? 0) >= 3;
}

bool isAdmin(String quarryId) {
  final entry = myAccess.firstWhereOrNull((a) => a.quarryId == quarryId);
  return (entry?.roleLevel ?? 0) >= 4;
}
```

**Уровни ролей для проверок:**
| `role_level` | `role_name` | Что позволяет |
|---|---|---|
| 1 | `user` | Читать отчёты, смотреть рекомендации |
| 2 | `surveyor` | + Загружать фото, запускать анализ |
| 3 | `blaster` | + Создавать паспорта, участки, скачивать отчёты |
| 4 | `admin` | + Управлять доступом, одобрять паспорта, создавать карьеры |

**Когда инвалидировать кэш:**
- После `PATCH /admin/users/{id}` (могла смениться роль)
- После получения 403 (права могли быть отозваны)
- При возврате приложения из фона (pull-to-refresh или `resume`)

**Бэкенд остаётся единственным авторитетом:** отображение кнопок — только UX-удобство, реальный guard — 403 от сервера.
